# UI Tests for the App

## Intent

Manual PR checks on the owner's iPhone take too much time. Most of them check how something looks or reads: suit inks on a theme, the felt edge, a VoiceOver label, the name field limit. A UI test target that runs in the simulator takes over those checks, so only what a simulator cannot show stays on the iPhone.

## Goals

- A UI test target that launches the real app in the simulator in fixed states, using the existing debug launch arguments.
- An accessibility audit (`performAccessibilityAudit()`, iOS 17) of the main screens in every theme, light and dark. Its contrast check would have caught #134.
- Behavior checks that today need hands on a device: the name field stops at 32 characters, and the own hole cards read "Your cards, hidden".
- One screenshot per checked state, kept in the test result, so the agent can judge the look (see "Results and screenshots").
- One documented command. The agent runs it before every PR that touches the app and ticks it in the PR checklist.

## Non-goals

- No CI job for now. The owner chose local runs because external contributions are rare so far. A CI job can come later, first as an optional check, then as a required one.
- No game flows: no hosting by taps, no hands played through, no payout checks. The package tests cover the game rules.
- No pixel comparison against reference images.
- No checks that need a real device: two devices on the network, lock screen, haptics, VoiceOver speech, real keyboards and IME.
- No custom VoiceOver actions. XCUITest cannot trigger "Show cards".

## Anti-goals

- Flaky tests. A test that fails at random teaches everyone to ignore it. Wait for elements with explicit timeouts and never use fixed sleeps.
- A long run. A full run should take a few minutes on the owner's Mac, short enough to run before every app PR.
- App code bent for tests. Accessibility identifiers are fine where a label is not stable. Test-only branches in the app are not, beyond the existing debug launch arguments.

## Constraints

- Swift 6 language mode. UI tests need XCTest (`XCUIApplication`); Swift Testing cannot drive UI. The UI test target is a deliberate exception to "Swift Testing for tests" in AGENTS.md, and AGENTS.md says so.
- `App/project.yml` defines the target; the project stays generated by xcodegen.
- iOS 17 deployment target; `performAccessibilityAudit` needs iOS 17 or later, so it is available.
- The app is English-only, but the simulator's locale changes number formats ("1.000"). Every launch pins `-AppleLanguages (en) -AppleLocale en_US`.
- SonarCloud analyzes the whole repo. The new test folder must be added to `sonar.coverage.exclusions`, like `Tests/**`.
- Game states start through launch arguments (`-debugTable`, `-debugStop lobby|turn|showdown|payout`, `-digitalCards`, `-fourColorDeck`, `-playerName`). A launch argument sets its `UserDefaults` key only for that launch, but it also wins over anything the Settings sheet writes. A test that switches theme or brightness in the Settings sheet must therefore not pass `-theme` or `-appearance`.
- Not everything is reset between launches. Every `-debugTable` launch writes a host save, so the next start screen shows "Resume game" and "Discard". A name typed into the name field stays saved too. Tests must reach a known state themselves (see "Clean state").
- The debug table plays with bots at their normal speed. Reaching the payout stop takes tens of seconds per launch, so the table is launched once per game state, not once per theme.

## Approaches

1. **XCUITest target (chosen).** A UI test target starts the real app, taps, reads labels and runs the accessibility audit. Screenshots are attachments in the result bundle. It costs the XCTest exception and a few accessibility identifiers. It is the only option that covers typing, labels and the audit.
2. **Snapshot tests of single views** (swift-snapshot-testing). Fast and deterministic, but a new dependency, no audit and no typing. Reference images break with Xcode rendering changes.
3. **Script around `simctl` with screenshots.** Cheapest, but it cannot type or audit, so half of the goals fall away.

The owner picked approach 1.

## Design

### Target and files

- New target `PokerChipCaseUITests` (`type: bundle.ui-testing`) in `App/project.yml`, with sources in `App/UITests/`, and in the test action of the `PokerChipCase` scheme.
- A small helper launches the app with a game state (debug table and stop, digital cards, four-color deck, player name, plus the pinned language and locale) and a helper switches theme and brightness through the Settings sheet.

### Checks

- **Theme sweep.** In one launch per screen, the test opens the Settings sheet, picks each of the 4 themes × Light and Dark, closes the sheet, runs `performAccessibilityAudit()` and attaches a screenshot. The start-screen sweep also audits and photographs the sheet in each combination; the table sweeps only use it to switch. Screens:
  - the start screen, clean (see "Clean state");
  - the debug table with physical cards, stopped at a turn (the default mode);
  - the debug table with digital cards and the four-color deck, stopped at the paid-out showdown (seat labels with `CardsText`, the ranking).
- **Start screen with a saved game.** Audited and photographed once, in the default theme, before the test discards the save.
- **Name field.** Type 40 characters into the name field; its value is the first 32.
- **Hole cards label.** At a digital debug table stopped at a turn, the own hole cards element reads "Your cards, hidden".

### Clean state

Before a start-screen check, the test taps "Discard" if a saved game is offered, and clears the name field before it types. The documented command does not erase the simulator.

### Findings that exist today

The first run will likely report audit findings in today's app. They become GitHub issues labeled `deferred`, `app` and `accessibility`: one issue per kind of finding and screen element, covering every theme and brightness where it shows up (e.g. "Contrast: seat label text on dark themes"), not one per combination. Each finding goes on an ignore list in the tests; each entry names its issue number and matches as narrowly as possible: audit type plus element. The tests are green from the first day and fail only on new findings. Fixing the listed findings is not part of this plan.

### Results and screenshots

- Screenshots are attachments that are always kept, named after the state (e.g. `table-payout-ruby-dark`).
- The agent exports them from the `.xcresult` bundle with `xcrun xcresulttool` and judges them, as in the agent's simulator checks.

### Workflow

- AGENTS.md gets the UI test command under "Commands", marked local-only (not in CI), and the layout entry for `App/UITests`. "It has no unit tests and is tested manually" changes accordingly.
- PR bodies list the UI test run as a ticked automatic gate when the PR touches `App/`.

## Left to the builder

- Which simulator the documented command names, and how a developer without it gets one.
- Accessibility identifiers: which elements need one and their names.
- How the ignore list is structured in code, as long as each entry carries its issue number.
- How to wait until the debug table has reached its stop.
- Splitting the checks into test methods, and keeping the run within a few minutes.
- Handling a local-network permission alert if the simulator shows one when the debug table hosts.

## Calls made during the design

- Theme and brightness are switched through the Settings sheet, not by relaunching, so the slow debug table starts once per game state. This keeps the run short without an app change such as a bot-speed launch argument.
- Tests reach a clean start screen by tapping "Discard", not by erasing the simulator or adding a reset argument.
- The turn table uses physical cards (the default mode) for the sweep; digital cards are covered at the payout stop and by the hole-cards check.
- Audit findings that exist today are grouped into one issue per kind of finding and element, not one per theme combination.
